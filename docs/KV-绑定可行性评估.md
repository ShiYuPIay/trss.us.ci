# Workers KV 命名空间绑定：可行性评估与实施方案

**评估对象**：`ShiYuPIay/trss.us.ci`（Vite + React 19 SPA，部署于 Cloudflare Workers 静态资源）
**评估日期**：2026-09-14
**结论**：**可行，且是本项目在当前形态下的正确选择。** 但 KV 的最终一致性与单键写入吞吐限制决定了它只能承载「读多写少」的负载，因此本方案对验证码、限流、媒体三类数据做了针对性规避设计。

---

## 一、先厘清根因：登录不可用不是「按钮坏了」

原项目是**纯静态资源型 Worker**——`wrangler.jsonc` 中没有 `main` 入口，因此不存在任何服务端代码。全部认证能力外包给腾讯 CloudBase：

| 环节 | 原实现 | 失效原因 |
| --- | --- | --- |
| 云环境识别 | `isCloudConfigured = Boolean(VITE_CLOUDBASE_ENV_ID && VITE_CLOUDBASE_PUBLISH_KEY)` | 凭据靠构建期注入（读 `/workspace/.env.tcb`，或 `process.env` 回退）。Cloudflare 构建环境两者都没有，编译产物中该常量为空 |
| 登录页 | `if (!isCloudConfigured) return toast.info('云服务正在准备中')` | 表单直接短路，用户看到的是「云服务正在准备」而非报错 |
| Google 登录 | 依赖外部 `VITE_OAUTH_RELAY_URL` 中继 + CloudBase 云函数 `oauth-callback` | 中继未配置 → 抛「Google 登录通道暂未配置」；云函数在仓库中不存在 |
| GitHub 登录 | 无 | 功能缺失 |
| 邮箱风控 | 无 | 任意一次性邮箱可注册 |
| 文章数据 | CloudBase 关系型数据库 | 未配置时 `fetchArticles` 直接返回示例数据，`createArticle` 抛「云服务正在准备」 |

**因此 KV 绑定与登录修复不是两件事，而是同一件事**：必须先有服务端运行时，才有地方承载会话、风控与 OAuth 回调。本方案为项目补上 `main` 入口（`worker/index.ts`），KV 命名空间正是这个运行时的状态层。

## 二、三类目标负载与 KV 的匹配度

| 数据类别 | 键空间 | 读/写比 | 单键写频率 | 一致性要求 | KV 适配结论 |
| --- | --- | --- | --- | --- | --- |
| 会话令牌 | `sess:*` | 极高（每请求 1 次） | 低（7 天续期一次） | 弱（可容忍秒级延迟） | **高度适配**，KV 的核心场景 |
| 邮箱验证码 | `otp:*` | 低 | 低 | 中（不可重放） | **适配**，靠 TTL + 校验即删兜底 |
| OAuth state / PKCE | `oauth:*` | 低 | 低 | 中（一次性） | **适配** |
| 限流计数 | `rl:*` | 中 | **高（同键递增）** | 强（需原子） | **降级使用**，见 §4.3 |
| 一次性邮箱黑名单 | `block:*` / `allow:*` | 极高 | 近零 | 弱 | **高度适配**，且支持热更新 |
| 文章内容与索引 | `article:*` | 高 | 低 | 弱 | **高度适配** |
| 媒体对象（≤2 MiB） | `media:*` | 高 | 低 | 弱 | **可用但非最优**，见 §4.5 |

**净结论**：6/7 类负载落在 KV 的设计甜点区（读放大、写稀疏、弱一致），唯一不匹配的是限流计数，已明确标注为 best-effort 并给出升级路径。

## 三、KV 能力边界（评估依据）

| 维度 | 指标 | 对本项目的影响 |
| --- | --- | --- |
| 读延迟 | 边缘缓存命中接近 0 ms；未命中回源约数十 ms。小于 1 MB 的值会被完整缓存 | 会话校验、文章读取走缓存，符合「优化资源访问速度」目标 |
| 写入可见性 | 同区域写入后通常立即可读；**跨区域传播最长约 60 秒** | 验证码校验需规避重放；注册后跨区域首次访问可能短暂 404 |
| 单键写吞吐 | 同一 key 约 1 次/秒（软限制），不同 key 可并发 | 限流计数不可视为强一致配额 |
| 值/键上限 | 值 25 MiB，键 512 字节，元数据 1 KiB | 媒体文件限 2 MiB，base64 后约 2.7 MiB，余量充足 |
| list 操作 | 单页最多 1000 键，需游标分页；结果最终一致 | 文章索引改为单键索引 + 前缀重建双保险 |
| 免费额度 | 读 10 万/天、写 1000/天、删 1000/天、list 1000/天 | 日均万级 PV 的文章站在额度内 |
| 付费额度 | Workers Paid \$5/月起，含 1000 万读 / 100 万写 / 100 万删 | 超出免费额度后的边际成本极低 |

## 四、关键设计决策与风险规避

### 4.1 会话令牌：不透明随机值 + HMAC 派生键

- 令牌为 32 字节 CSPRNG 随机值的 base64url，**本身不含任何用户信息**；
- KV 中存的键是 `HMAC(SESSION_SECRET, "session:" + token)`，而非明文或裸哈希。这样即使 KV 内容被读取，缺少密钥也无法构造可用会话键；
- 7 天 TTL；剩余有效期不足 50% 时滑动续期，把写入摊薄到每 3.5 天一次，避免「每次请求都写 KV」这一 KV 反模式；
- 缺失 `SESSION_SECRET` 时在**签发阶段立即失败**（`server_misconfigured`），不静默降级。

> 实测修正：初版 `createSession` 未强制校验 `SESSION_SECRET`（因为令牌是随机的，不需要签名），集成测试暴露了这一点。已改为密钥派生会话键，既补齐了纵深防御，也让配置缺失 fail-fast。

### 4.2 邮箱验证码：规避最终一致性下的重放

风险：若验证码校验后不立即失效，跨区域传播窗口内可能被重放。三层规避：

1. 只存 `HMAC(SESSION_SECRET, "otp:" + email + ":" + code)` 指纹，KV 泄漏也无法直接冒用（有测试断言 KV 中不含明文）；
2. TTL 300 秒 + 最多 5 次尝试，超限直接删除；
3. **校验通过后立即删除**，并额外施加「每邮箱 10 分钟 12 次」的校验限流。

实测：重放同一验证码返回 `otp_expired`，符合预期。

### 4.3 限流：明确定位为第一道闸门

KV 的读-改-写非原子，并发突发下计数可能偏低。因此：

- 定位为「削弱暴力破解与批量注册」，**不是强一致配额**；
- 读/写失败时**放行**（fail-open），避免 KV 抖动放大成全站不可登录；
- 登录成功清零计数，避免正常用户被历史失败次数拖累。

**升级路径**（按需选择，均不影响现有接口契约）：
1. **Rate Limiting Binding**（`[[ratelimits]]`）：Cloudflare 原生原子限流，配置即可，最省事；
2. **Durable Object**：需要跨请求强一致计数或分布式锁时使用。

### 4.4 文章索引：单键索引 + 前缀重建双保险

列表页只读 1 个索引键（`articles:index`），避免每次 list 全部文章。若索引键因最终一致性或误删而缺失，则按 `article:` 前缀重建并回写，避免单键成为单点。

### 4.5 媒体对象：可用，但生产应换 R2

KV 值上限 25 MiB，本方案限制单文件 2 MiB，以 base64 存入 `SITE_KV`，通过 `/api/media/:id` 回源并带 `immutable` 缓存头。

- **优点**：零额外基础设施即可跑通封面与附件上传，不引入新计费项；
- **代价**：base64 带来约 33% 存储膨胀；KV 写额度（免费 1000 次/天）是主要约束；
- **建议**：当单日上传超过约 100 次或需要 >2 MiB 文件时，把 `worker/routes/media.ts` 换成 R2 绑定（`env.MEDIA_BUCKET.put/get`），接口契约不变。

### 4.6 邮箱风控：三层判定 + KV 热更新

判定顺序：**KV 白名单 → KV 黑名单 → 内置清单 → 关键词启发式 → 风险 TLD / 本地部分规则**。

- 内置约 700 条一次性邮箱域名（覆盖 mailinator、guerrillamail、10minutemail、yopmail 及其别名域）；
- 关键词启发式覆盖尚未进入清单的新服务（`tempmail`、`throwaway`、`10minute` 等 90 余个词根）；
- 高风险免费 TLD（`.tk/.ml/.ga/.cf/.gq/.cm` 等）；
- **KV 覆盖层支持热更新**：写入 `block:<domain>` 或 `allow:<domain>` 即刻生效，无需重新部署；
- 风控同时作用于**注册、密码登录、验证码请求/校验，以及 OAuth 回调返回的邮箱**——这条最容易漏，有独立测试覆盖。

> 已知限制：Workers 运行时无法做 DNS/MX 查询，因此无法校验域名是否真实可收信。若需该能力，应引入 DoH 查询（如 Cloudflare DNS over HTTPS）作为第 6 层判定。

## 五、性能与成本量化

| 场景 | KV 操作数 | 说明 |
| --- | --- | --- |
| 会话校验（每 API 请求） | 1 读 | 命中边缘缓存时近乎零延迟 |
| 文章列表页 | 1 读（索引）+ N 读（文章，N ≤ 200） | 单页限制上限，避免读放大失控 |
| 文章详情页 | 1 读 | |
| 邮箱注册/登录 | 1–2 读 + 1 写 | |
| 验证码登录 | 2 读 + 2 写 + 2 删 | |
| OAuth 登录 | 2 读 + 1 写 + 1 删 | |

**容量推算**：日均 1 万 PV 的文章站，约 2–3 万次 KV 读/天，落在免费额度（10 万读/天）内；写入主要来自登录与发文，日均百级，远低于 1000 次/天。**即免费额度可支撑，无需付费即可上线。**

对比原方案：CloudBase 需要包年云环境，且凭据注入与 Cloudflare 构建环境存在结构性冲突（这正是当前故障的成因）。

## 八、最终结论

1. **KV 绑定可行且必要**：它同时解决了「资源访问速度」（边缘缓存 + 单键索引）、「数据存储吞吐量」（读多写少负载天然契合）与「身份验证令牌管理」（不透明令牌 + 密钥派生键 + TTL）三个目标，且免费额度足以支撑当前量级。
2. **登录修复必须依托 Worker 运行时**：原故障是架构性缺位，而非配置错误；仅调整环境变量无法修复。
3. **KV 不是万能存储**：限流计数与高频写入同键的场景必须规避或升级，媒体存储在大文件/高频上传场景应换 R2。这些边界已在实现中显式标注，不做隐性假设。
