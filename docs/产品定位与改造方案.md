# 产品定位与改造方案：从博客到写作工作台

> 前提：域名保持 `trss.us.ci` 不变；使用者为**开放注册的公众用户**。
> 本文回答四个问题：整体定位是什么、核心功能有哪些、页面结构如何组织、与现有博客形态的本质区别在哪。
> 全部改造建议基于对现有代码的实测边界（见 §6），不假设尚未具备的能力。

---

## 0. 结论摘要

**推荐方向：以「写作项目」为第一公民的写作工作台（Writing Project Workspace）。**

一句话定位：

> **面向中文深度内容创作者的写作项目管理工具——把「写一篇长文 / 一个系列」当作项目来推进，而不是把「文章」当作产物来陈列。**

三个决定性的设计决策：

| # | 决策 | 理由 |
| --- | --- | --- |
| 1 | **第一公民从「文章」换成「写作项目」** | 这是与博客分道扬镳的根本点。文章是**已完成、已发布**的产物；项目是**有生命周期、可迭代**的过程 |
| 2 | **登录后首页是「工作台」，不是「内容列表」** | 博客的登录态是管理后台（附属功能）；本产品的登录态就是产品主体 |
| 3 | **公开发布降级为「项目的输出形态」** | 阅读页按**项目结构**（系列 / 小册子目录）呈现，不是时间流。博客只是本产品的一个输出口，不是它的形态 |

**必须先说清楚的判断**：**这个方向能否成立，取决于是否收敛到一个利基。** 通用写作工具赛道已被 语雀 / Notion / Obsidian / 飞书文档 占满，一个人做通用工具没有胜算。本文给出的是**产品骨架**；骨架之上必须选一个具体人群（§8.1 列出候选），否则改造得再完整也只是"另一个笔记工具"。

---

## 1. 为什么「给博客加功能」不会让它变成 web 应用

这是最容易走偏的地方。判断一个站点是「应用」还是「博客」，不看功能数量，看**三件事**：

| 判据 | 博客 | Web 应用 |
| --- | --- | --- |
| **第一公民是什么** | 内容（文章） | 用户的任务对象（项目 / 文档 / 工单…） |
| **登录后首页是什么** | 内容列表 / 管理后台 | 工作台（待办 + 进行中 + 进度） |
| **用户是否有状态** | 无（读者无状态，作者只有"发布"一个动作） | 有（草稿、进度、版本、目标、连续天数） |

按这三条检验现状：

| 现状 | 判定 |
| --- | --- |
| 首页是精选文章轮播 + 文章列表 + 快捷入口 | ❌ 内容陈列 |
| `/studio` 是编辑器，登录后进入 | ❌ 管理后台形态（博客的附属） |
| 全站只有一种内容类型（`article`） | ❌ 单一内容模型 |
| 文章有 `status`（draft/published） | ⚠️ 雏形，但没有"进行中"的概念 |
| 用户模型完整、`articles` 带 `user_id` | ✅ **多用户基础已具备，只是界面按单作者设计** |

**结论**：现状是"一个功能完整的博客"，不是"一个功能少的应用"。所以改造不是加功能，而是**换第一公民**。

## 2. 整体定位

### 2.1 一句话定位

> 面向中文深度内容创作者的**写作项目管理工具**：把长文与系列当作项目推进，从选题到发布全程可追踪。

### 2.2 定位的三层展开

| 层 | 内容 |
| --- | --- |
| **服务谁** | 写长文 / 系列 / 小册子的中文创作者（非"随手记笔记"人群） |
| **解决什么** | 长文写作**容易半途而废**：没有进度感、没有结构、素材散落、版本混乱、发布后无法迭代 |
| **凭什么** | 把"写作"从**一次性动作**变成**可管理的项目**：有状态、有结构、有进度、有版本 |

### 2.3 明确不做（边界）

划清边界比罗列功能更能守住定位：

- ❌ **不做通用笔记工具**（不抢 Obsidian / Notion 的"第二大脑"定位）
- ❌ **不做时间流博客**（不提供"发布短文到时间线"这类功能——那是把产品拉回博客）
- ❌ **不做社区 / 论坛**（评论、点赞、关注只做"轻互动"，不做信息流）
- ❌ **不做多人协作编辑**（实时协同的复杂度与一人公司的维护能力不匹配）
- ❌ **不做富文本 WYSIWYG**（坚持 Markdown，这是创作者工具的一致性）

## 3. 核心功能

按"支撑定位的必要性"排序，而非按开发顺序。

### 3.1 项目（Project）—— 第一公民

| 能力 | 说明 |
| --- | --- |
| 项目类型 | 长文 / 系列 / 小册子（决定公开阅读页的呈现结构） |
| 状态机 | `构思 → 大纲 → 撰写 → 修订 → 已发布 → 迭代中`（**可回退**，不是单向流） |
| 项目目标 | 目标字数、截止日、计划章节数 |
| 两种视图 | 看板（按状态分组）/ 列表（按更新时间） |
| 进度计算 | 已完成字数 / 目标字数；已完成章节 / 计划章节 |

> **为什么"状态机可回退"很重要**：博客的 `published` 是终点；项目的 `已发布` 只是里程碑——发布后继续改会进入 `迭代中`，并产生新版本。这是"项目"与"文章"最实质的差别。

### 3.2 大纲（Outline）

- 章节树，支持拖拽排序与层级嵌套
- **从大纲一键生成草稿骨架**（每章生成空草稿，继承标题）
- 每章独立的目标字数与状态
- 大纲即公开阅读页的目录来源

### 3.3 草稿与版本

| 能力 | 说明 |
| --- | --- |
| 自动保存 | 沿用现有编辑器的即时保存思路 |
| 版本快照 | 手动"存档"或按里程碑自动存档 |
| 版本对比 | 两版之间的 diff（Markdown 层面） |
| 章节级编辑 | 一次只专注一章，而不是一篇超长文 |

> **章节级编辑是核心体验差异**：博客编辑器给你一个 5000 字的空文本框；本产品给你一棵章节树，每次只面对一章。

### 3.4 素材库（Library）

- 图片（**复用现有上传能力**）、引用、参考链接
- 素材可被多个项目引用，显示"被引用于"反向索引
- 统一管理，避免同一张图重复上传

### 3.5 发布（Publish）

| 能力 | 说明 |
| --- | --- |
| 本站发布 | 项目 → 公开阅读页（按项目结构呈现） |
| 导出 | 导出 Markdown（单文件 / 按章节拆分） |
| 外部分发 | 复制为适配格式，便于投递到其它平台 |
| 迭代 | 发布后可继续编辑 → 生成新版本，读者看到的是最新版 |

### 3.6 公开输出（Public）

- 项目可设为公开 / 私有（**默认私有**，创作者工具应默认保护草稿）
- 公开阅读页按**项目结构**呈现（系列 / 小册子的目录树），不是时间倒序
- 读者侧只做轻互动：收藏、订阅作者更新（**不做评论区**——见 §2.3）

### 3.7 写作数据（Stats）

连续写作天数、字数趋势、项目完成率、平均完成周期、草稿停留时长。

> 这一模块是"应用感"的关键来源之一：**它提供的是关于"你"的数据，不是关于"内容"的列表**。

### 3.8 账号（Account）

- **复用现有**：邮箱验证码 / 密码 / Google / GitHub 登录、一次性邮箱拦截、限流
- **新增**：`handle`（公开用户名，用于 `/u/:handle`）、个人简介、隐私默认值

## 4. 页面结构

### 4.1 路由总表

| 路由 | 状态 | 归属 | 说明 |
| --- | --- | --- | --- |
| `/` | **改造** | 未登录 = 落地页 / 已登录 = 工作台 | 同一路径按登录态分流 |
| `/projects` | 新增 | 工作台 | 项目看板（默认视图） |
| `/projects/new` | 新增 | 工作台 | 新建项目 |
| `/projects/:id` | 新增 | 工作台 | 项目详情：大纲 / 章节 / 素材 / 发布 |
| `/projects/:id/write/:chapterId` | 新增 | 工作台 | 章节编辑器（专注模式） |
| `/projects/:id/versions` | 新增 | 工作台 | 版本列表与对比 |
| `/library` | 新增 | 工作台 | 素材库 |
| `/stats` | 新增 | 工作台 | 写作数据 |
| `/settings` | 新增 | 工作台 | 账号、handle、隐私 |
| `/explore` | 新增 | 公开 | 公开项目广场 |
| `/p/:slug` | 新增 | 公开 | 公开项目阅读页（系列/小册子结构） |
| `/u/:handle` | 新增 | 公开 | 作者主页 |
| `/login` | 复用 | 公开 | 登录 / 注册（现有三页签 + OAuth） |
| `/auth/callback` | 复用 | 公开 | OAuth 回调（现有） |
| `/articles` | **降级** | 公开 | 保留为重定向 → `/explore`，避免旧链接失效 |
| `/articles/:slug` | **降级** | 公开 | 保留为重定向 → `/p/:slug` |
| `/tags` | 移除 | — | 标签体系被"项目 + 章节"取代 |
| `/about` | 保留 | 公开 | 改为产品介绍 / 关于团队 |
| `/studio` | **移除** | — | 由 `/projects` 取代 |
| `*` | 复用 | 公开 | 404（现有） |

### 4.2 信息架构

```
未登录
  /                       落地页：这是什么 / 示例项目 / 注册入口
  /login /auth/callback   认证
  /explore /p/:slug /u/:handle   公开内容（可读，无需登录）
  /about                  产品介绍

已登录 —— 工作台（产品主体）
  /                       今日待办 · 进行中项目 · 目标进度
  ├─ /projects            项目看板（按状态分组）
  │    └─ /projects/:id
  │         ├─ 大纲        章节树
  │         ├─ 章节        → /projects/:id/write/:chapterId
  │         ├─ 版本        → /projects/:id/versions
  │         ├─ 素材        项目引用的素材
  │         └─ 发布        发布设置 / 导出
  ├─ /library             素材库（跨项目）
  ├─ /stats               写作数据
  └─ /settings            账号 · handle · 隐私
```

### 4.3 关键页面的设计要点

**`/`（登录后 · 工作台）** —— 这一页决定产品是不是应用

必须回答"我现在该做什么"，而不是"我写过什么"：

| 区块 | 内容 |
| --- | --- |
| 今日待办 | 有截止日的项目、卡在"修订"超过 N 天的项目 |
| 进行中 | 按状态分组的项目卡片，带进度条 |
| 目标进度 | 本周字数 / 连续写作天数 |
| 快捷动作 | 新建项目、继续上次编辑 |

**禁止**出现"最新文章列表"——那会把首页拉回博客形态。

**`/projects/:id`** —— 项目详情是"控制台"，不是"编辑页"

左侧大纲树 + 中间当前章节内容 + 右侧素材/版本面板。三个面板都可折叠，窄屏降级为标签切换。

**`/p/:slug`（公开阅读页）** —— 与博客文章页的根本区别

- 顶部是**项目目录树**（系列显示章节列表，小册子显示章节目录）
- 阅读进度条贯穿全篇
- 文末是"下一章"而非"相关文章"
- 显示**版本信息**（第几版、最后更新时间）——这是"可迭代"的可见证据

## 5. 与博客 / 个人网站的关键区别

| 维度 | 博客 / 个人网站（现状） | 本项目（写作工作台） |
| --- | --- | --- |
| **第一公民** | 文章（已完成、已发布） | **写作项目**（有生命周期、可迭代） |
| **首页（登录后）** | 精选文章轮播 + 文章列表 | **工作台**：待办 + 进行中 + 目标进度 |
| **首页（未登录）** | 直接展示内容 | **落地页**：说明产品做什么 |
| **用户角色** | 1 个作者 + N 个读者 | N 个作者，**人人有自己的工作台** |
| **登录的意义** | 进入管理后台（博客的附属） | **进入产品主体** |
| **核心数据** | 文章正文 | 项目状态 · 大纲 · 版本 · 进度 · 素材引用 |
| **内容组织** | 时间流 + 标签 | **项目 → 章节树**；系列 / 小册子为一级形态 |
| **时间观** | 发布时刻（时间倒序） | 项目周期（进行中的过程） |
| **发布** | 终点 | **里程碑**（发布后仍可迭代出新版本） |
| **"进行中"的内容** | 不存在（草稿不可见、无状态） | **核心可见对象**（看板上的卡片） |
| **价值来源** | 读者读到内容 | **作者把项目推进到完成** |
| **读者侧形态** | 文章列表 → 文章页 | 项目广场 → **项目目录树** |
| **标签的作用** | 检索入口 | 移除（被项目结构取代） |
| **数据可见性** | 无 | **写作数据看板**（关于"你"的指标） |

**一句话概括差异**：博客的中心是**已完成的产物**，本产品的中心是**未完成的进行时**。

## 6. 从现有代码改造的路径

### 6.1 直接复用（几乎不动）

| 模块 | 路径 | 说明 |
| --- | --- | --- |
| 账号体系 | `worker/routes/auth.ts` | 验证码 / 密码 / OAuth / 登出 / 会话，全部可复用 |
| 安全与风控 | `worker/lib/{session,oauth,email-guard,disposable-domains,crypto,mailer,rate-limit}.ts` | 一次性邮箱拦截 + 限流是开放注册的基础设施，已具备 |
| 用户模型 | `worker/lib/users.ts` | 已含 `uid / email / name / avatar_url / provider / email_verified`，**多用户基础已在** |
| KV 抽象 | `worker/lib/store.ts` | 键设计清晰（`article:<slug>` / `articles:index`），扩展为 project 即可 |
| 媒体上传 | `worker/routes/media.ts` | 图片上传 / 回读可复用为素材库底座 |
| 编辑器 | `src/pages/Studio.tsx` | Markdown 编辑 + 封面上传，作为章节编辑器的起点 |
| 视觉体系 | `src/index.css` | 全部设计令牌无需改动，新页面沿用 |

### 6.2 需要改造

| 项 | 现状 | 改造方向 |
| --- | --- | --- |
| 数据模型 | 只有 `article` | 引入 `project` + `chapter`；或给 `article` 加 `project_id` / `order` / `type` |
| KV 键 | `article:<slug>` / `articles:index` | `project:<id>` / `chapters:<projectId>` / `projects:index` |
| 路由 | `/studio` 是编辑器 | 换成 `/projects` 体系；`/articles*` 保留为重定向 |
| 首页 | `src/pages/Index.tsx` 是文章展示 | 改为工作台（登录态）/ 落地页（未登录） |
| `status` 字段 | 仅 `draft` / `published` | 扩展为项目状态机（6 态，可回退） |

### 6.3 需要新增

- 项目 / 大纲 / 版本 / 素材 的 CRUD 与页面
- 版本 diff（Markdown 层面即可，不必做富文本 diff）
- 写作数据聚合（按天聚合字数，KV 存聚合结果而非逐条明细）
- 公开项目阅读页 + 作者主页 + 广场
- `handle` 分配与校验

## 7. 开放注册必须补齐的能力

开放注册改变了威胁模型。**现有基础已经不错，但以下五项缺失会让公开运营出问题**：

| # | 能力 | 现状 | 为什么必须 |
| --- | --- | --- | --- |
| 1 | **handle 唯一性与保留字** | 无 | `/u/:handle` 需要；必须挡掉 `admin` / `api` / `login` 等保留字，否则会被抢注成钓鱼入口 |
| 2 | **存储与发布配额** | 无 | KV 单值上限 25 MB，**图片走 KV 会迅速撞配额**。公开运营前建议把媒体迁到 R2，并按用户设配额 |
| 3 | **内容审核与举报** | 无 | 有公开页面就必须有举报入口与下架能力，否则平台要为 UGC 承担责任 |
| 4 | **用户封禁** | 无 | 需要黑名单（可复用现有 `BLOCKLIST_KV` 的模式） |
| 5 | **默认隐私** | 无 | 项目默认**私有**；只有用户主动公开才出现在广场与作者主页 |

**已具备、无需新增的**：一次性邮箱拦截（约 700 条域名 + 启发式）、IP 限流、OAuth 邮箱验证强制。

> 若要进一步防机器人注册，可加 Cloudflare Turnstile——它可与现有 Workers 部署天然集成，且不引入第三方账号体系。

## 8. 风险与取舍

### 8.1 最大风险：没有差异化（必须正视）

通用写作工具赛道已被占满。**产品骨架不解决这个问题——只有利基能解决。** 三个候选收敛方向：

| 候选 | 收敛方式 | 代价 |
| --- | --- | --- |
| **A. 按体裁收敛** | 只服务"写系列 / 小册子"的人（多数工具只优化单篇） | 人群较窄，但需求明确 |
| **B. 按领域收敛** | 服务某个垂直领域的作者（如技术长文、行业研究、课程讲稿） | 需要该领域的信任背书 |
| **C. 按工作流收敛** | 只做"从大纲到发布"这一段，不做笔记、不做知识管理 | 需与上游工具做好导入导出 |

**建议**：先选 B（领域收敛），因为它同时解决了"差异化"与"冷启动获客"两个问题——领域内的人有共同聚集地，比泛人群更容易找到前 100 个用户。

### 8.2 其他风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| **冷启动** | 开放注册但没人来 = 空城，广场全空反而降低信任 | **先邀请制 + 公开阅读**，有内容后再开注册；或开放注册但广场只展示精选 |
| **KV 不适合多用户内容存储** | 图片走 KV 会撞配额；列表页靠单键索引，用户量上来后并发写会冲突 | 公开运营前把媒体迁 R2；索引拆分为按用户分片 |
| **一人维护成本** | 审核、举报、客服都需要人 | 审核先做"举报 + 人工下架"，不做自动审核 |
| **域名品牌偏弱** | `trss.us.ci` 是个人化命名，作为公众产品品牌记忆度低 | 域名可不变（已确定），但建议做**品牌层**：产品名独立于域名，域名只作技术入口 |
| **与现有内容的关系** | 现有 6 篇示例文章是旅行/生活随笔，与新定位不符 | 把它们作为**示例项目**保留（正好演示"项目"形态），但首页不再展示 |

### 8.3 需要明确的取舍

1. **不保留 `/tags`**：标签是博客的检索手段，项目结构取代了它。保留会让信息架构出现两套并行的组织方式。
2. **不做评论**：评论区是最重的运营负担，且会把产品拉向社区。轻互动（收藏 + 订阅）足够。
3. **`/articles` 保留为重定向**：不删路径，避免已有外链失效——这是 SEO 上的必要妥协。

## 9. 实施顺序建议

| 阶段 | 内容 | 依赖 | 说明 |
| --- | --- | --- | --- |
| **P0** | 数据模型（project / chapter）+ 项目 CRUD + 项目看板 | 无 | 换第一公民，最小可用闭环 |
| **P1** | 大纲 + 章节编辑器 + 版本 | P0 | 让"项目"真正可推进 |
| **P2** | 素材库 + 发布 + 公开阅读页 | P1 | 打通输出 |
| **P3** | 写作数据 + 作者主页 + 广场 | P2 | 应用感与公开维度 |
| **P4** | 开放注册的治理能力（举报 / 封禁 / 配额） | P2 | **开注册之前必须完成** |
| **P5** | 媒体迁 R2 | P4 | 公开运营前完成 |

**P0 完成即可验证方向**：如果"项目看板"这个形态你自己都不愿意每天打开，就不必继续往下做。

## 附录：判断改造是否走偏的自检清单

每完成一个阶段，用这几条自检：

- [ ] 登录后首页是不是**待办 / 进行中 / 进度**，而不是内容列表？
- [ ] 未登录首页是不是**产品说明**，而不是内容陈列？
- [ ] 有没有出现"按时间倒序的内容流"？有就是走偏了
- [ ] 用户有没有**可积累的状态**（草稿、版本、进度、连续天数）？
- [ ] 核心对象是"项目"还是"文章"？如果是后者，说明只是换了皮肤
- [ ] 公开页面呈现的是**项目结构**还是**时间流**？
- [ ] 新加的功能是在强化"把项目推进到完成"，还是在增加"内容陈列"的花样？
